可以，二期这三块其实要做成一个闭环，而不是三个独立功能：

> **患者选择模型**负责算“患者会不会来”；
> **医院资源模型**负责算“来了以后能不能接”；
> **战略推演2.0**负责把战略动作转成参数变化，反复计算不同方案的结果。

最终就是：

```text
战略动作
   ↓
患者选择概率变化
   ↓
潜在新增患者
   ↓
医院资源承载约束
   ↓
实际可承接患者
   ↓
HRI / 辐射半径 / 资源压力变化
   ↓
A/B/C方案比较
```

下面建议直接按这套技术方案建设。

# 二、患者选择模型

这是二期最核心的模型。

## 1. 模型要解决什么

不要直接预测：

> “明年有多少患者。”

而是预测：

> **某个区域、某个病种/专科的患者选择你院的概率是多少。**

即：

$$
P(选择我院)
$$

例如：

```text
城阳某街道
心内科患者

当前选择我院概率：12.8%

如果：
心内科能力 +20%
专家下沉
医联体合作增强

重新计算：

选择概率：18.6%
```

这样才具备战略推演能力。

---

> **街道 × 科室 × 年/月**

不要一开始做患者个人级模型。

一条训练数据类似：

| 街道 | 月份 | 科室 | 人口 | 距离 | 我院患者 | 竞争医院数 | HRI |
| -- | -- | -- | -: | -: | ---: | ----: | --: |

增加以下特征。

### 区域侧

```text
人口
人口增长率
年龄结构
街道到医院距离
驾车时间
```

### 医院侧

```text
专科医生数
高级职称数
床位
门诊量
手术量
专科能力指数
```

### 历史行为侧

```text
去年同期患者数
过去3月患者数
复诊率
HRI
历史患者占比
```

### 竞争侧

```text
5km内医院数
10km内三级医院数
最近竞争医院距离
竞争专科能力
```

### 协作侧

```text
是否存在医联体
历史转诊量
专家下沉次数
```

# 四、患者选择模型怎么建

第一版建议同时保留两个模型。

## 模型A：Logistic Regression

作用：

> 可解释基线模型。

好处是领导和评委容易理解：

```text
距离增加 → 选择概率下降
专科能力增强 → 选择概率提高
医联体增强 → 选择概率提高
```

---

## 模型B：LightGBM

作为真正计算模型。

原因：

* 能处理非线性关系；
* 对表格数据适合；
* 训练速度快；
* 对你这种几年、134街道、多个科室的数据量很合适。

不要上神经网络。

没必要。

---

# 五、SHAP负责解释结果

例如系统推演以后发现：

> 城阳心内科选择概率从12.8%提高到18.6%。

SHAP告诉你主要原因：

```text
专科能力提升       +2.8%
医联体合作         +1.9%
距离因素           -1.1%
历史复诊优势       +1.4%
竞争医院影响       -0.6%
```

前端显示：

### 患者选择驱动因素

这样模型不再是黑箱。

# 六、一个重要问题：你只有自己的患者数据

如果拿不到竞争医院患者数据，你严格来说无法知道：

> “所有患者中有多少选择了我院。”

所以一期/二期第一版建议不要直接称：

> “真实患者选择概率。”

可以定义为：

# Patient Attraction Score

### 患者吸引力指数

根据：

```text
我院患者率
+
人口
+
距离
+
专科能力
+
历史行为
+
竞争环境
```

计算一个0—100吸引力分数。

等以后拿到医保/区域平台数据，再升级成真正的“医院选择概率模型”。

这个统计口径要严谨。

# 七、医院资源模型

患者选择模型计算的是：

> 潜在需求。

但战略推演不能到这里结束。

第二层必须判断：

> 医院有没有能力接。

# 八、资源模型建议不要建成一个总容量

一定要：

> **科室级资源容量模型**

例如心内科：

```text
医生
门诊号源
床位
检查能力
手术/介入能力
护理能力
```

每个专科瓶颈不同。

# 九、一期资源模型至少收这些数据

每个科室：

| 指标      | 作用    |
| ------- | ----- |
| 医生人数    | 基础供给  |
| 出诊医生数   | 门诊供给  |
| 日均号源    | 门诊容量  |
| 日均门诊量   | 当前负荷  |
| 床位数     | 住院容量  |
| 床位使用率   | 住院负荷  |
| 平均住院日   | 周转能力  |
| 年住院患者   | 当前业务量 |
| 手术/介入量  | 手术容量  |
| 手术资源利用率 | 手术负荷  |

# 十、资源容量模型不用复杂AI

第一版用公式和约束模型最好。

例如门诊：

$$
剩余门诊容量=
可开放号源-实际门诊量
$$

住院：

$$
床位可承接量
=
床位数\times365/平均住院日
$$

再乘合理利用率。

手术：

$$
剩余手术能力=
最大可排台次-当前实际台次
$$

最终：

$$
实际新增患者
=
min(
潜在新增患者,
门诊容量,
住院容量,
手术容量
)
$$

注意实际实现时不同患者路径要分开算，不是简单三个数直接取min。

# 十一、建议增加“瓶颈识别”

这是资源模型最有价值的输出。

例如推演：

> 城阳心内科加强20%

患者选择模型得到：

```text
潜在新增门诊：5200
潜在新增住院：620
```

资源模型算：

```text
门诊还能承接：4100
住院还能承接：700
```

最终：

```text
实际新增患者：4100左右

主要瓶颈：
门诊号源
```

系统显示：

> **战略需求存在，但现有门诊能力将限制约21%的潜在增长。**

这就有管理价值了。

# 十二、资源模型最好输出四个等级

建议：

```text
资源利用率 <75%       充足
75%-85%              正常
85%-95%              紧张
>95%                 瓶颈
```

具体阈值以后按医院管理标准调整。

地图或科室面板可以直接显示：

```text
心内科
门诊：🔴
床位：🟠
手术：🟢
```

# 十三、战略推演2.0是什么

一期可能是：

> “心内科能力+20%，患者增加多少。”

二期要升级为：

> **多个战略动作同时发生 + 多年份演化 + 资源约束 + 不确定性 + 多方案比较。**

这是2.0真正的变化。

### 增加床位

```text

```

# 十七、多年份不能简单乘3

这是战略推演2.0必须改的一点。

例如：

2027增长10%。

2028不能继续：

```text
2026患者 × 1.2
```

而应该：

```text
2027结果
成为
2028新的基线
```

即：

```text
2026
 ↓
战略动作
 ↓
2027状态
 ↓
人口变化+资源变化
 ↓
2028状态
 ↓
继续演化
 ↓
2029
```

这才是真正的动态推演。

# 十八、必须增加三情景

# 十九、A/B/C方案比较

这是2.0必须有的前端功能。

例如：

### A

心内科提升20%

### B

心内科提升20% + 医联体

### C

心内科提升20% + 医联体 + 增加门诊容量

输出：

| 指标     |     A |     B |      C |
| ------ | ----: | ----: | -----: |
| 新增患者   |  3200 |  5100 |   6800 |
| HRI提升  | +0.14 | +0.22 |  +0.29 |
| 服务人口提升 |   12万 |   18万 |    24万 |
| 门诊负荷   |   94% |  103% |    88% |
| 资源瓶颈   |     高 |     高 |      低 |
| 综合得分   |    76 |    81 | **92** |

这个表比单一预测非常有价值。

仍然放最后。

不要让DeepSeek计算战略结果。

```text

基准结果
保守结果
乐观结果
资源瓶颈
主要驱动因素
```

输出：

例如：

这样大模型只负责：

> 解释模型。
